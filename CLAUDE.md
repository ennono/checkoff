# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CheckOff is a WordPress plugin (v3.8.0, text domain `checkoff`) that lets visitors build their own multi-level checklists from building blocks and tick them off. Structure and implementation follow the sister plugin **MixMyMeals** (`ennono/mixmymeals`): singleton main class, a settings class with tabs, an admin API that renders the fields, one class per concern in `includes/lib/`, shortcodes and their AJAX handlers in one class, jQuery frontend with a debug and a `.min.js` flavour, catalogue in `lang/`.

## Prefixes

- PHP classes `Checkoff_*`, files `class-checkoff-*.php`, functions `checkoff_*`, options and transients `checkoff_*`, filters/actions `checkoff_*`.
- Post types `cko_checklist` and `cko_subscription`, tables `{prefix}checkoff_values` and `{prefix}checkoff_versions`, post meta `_cko_*` / `_cko_sub_*`, shortcodes `cko_*`, AJAX actions `cko_*`, CSS classes `cko-*`, query parameter `cko`.
- Source language English; German in `lang/checkoff-de_DE.{po,mo,l10n.php}`.

## Architecture

### Bootstrap

`checkoff.php` requires all class files → `checkoff()` creates `Checkoff::instance()` and `Checkoff_Settings` → wrapper methods instantiate post types, meta boxes, shortcodes, cleanup and privacy.

### Data model

**3.0.0 is a clean cut, by the user's decision: nothing from before is carried over** — no tick IDs, no old value formats, no old tree format, no `cko_round` posts. The update (`Checkoff_Schema::maybe_install()`, option `checkoff_schema` = 3, also run on activation) creates the tables, keeps each list's structure (as revision 1) and its password level, and deletes everything else of the old model (`remove_before_3()`). Don't add compatibility code for older data.

Where things live:

| Where | What |
|---|---|
| `cko_checklist` post | one checklist; post title = its title; not public, no permalink, `create_posts` disabled (made on the frontend only) |
| `_cko_public_id` (meta) | the random ID in the link (stored lower case, no dashes) |
| `_cko_access` (meta) | `open` \| `protected` \| `private` — stored, not derived; protected/private without a hash reads as open |
| `_cko_password` (meta) | hash (`wp_hash_password()`), only with protected/private |
| `_cko_listed` (meta) | `'1'`: in the public directory (counts only while protected) |
| `_cko_last_access` (meta) | unix time, written at most once an hour on views |
| `_cko_template*` (meta) | template flag, description, key |
| `{prefix}checkoff_versions` | `(checklist_id, revision)` PK → `structure` (JSON), `saved_at` (UTC). One row per structure save; the newest is the list as it is (`Checkoff_Versions`) |
| `{prefix}checkoff_values` | `(checklist_id, round, entry_id)` PK → `value` (JSON, NULL = nothing), `stage` (NULL \| `doing`), `set_at` (UTC). One row per entry and round (`Checkoff_Values`, the only class touching the table) |
| `cko_subscription` post | an e-mail subscription (see below) |

**The public ID is the only way in.** `Checkoff_Public_Id` generates it (alphabet without 0/o/1/l/i, length setting, default 12 ≈ 59 bits), normalises input (case, spaces, dashes) and formats it in groups of four. The post ID never reaches the frontend — `Checkoff_Checklist::to_client()` is what the browser gets. Failed lookups are rate-limited per visitor (`Checkoff_Rate_Limit`, salted IP hash in a transient); once the limit is reached every lookup is refused for the hour, correct ones included, or the refusal would tell a guesser when they hit.

**One link, three levels (2.0.0) — no accounts, on purpose.** The address shows the list; a password protects it. `Checkoff_Checklist::get_level()` reads `_cko_access` (stored since 3.0.0), but a level needing a password reads as open while there is no `_cko_password`: **open** (the address views, ticks and edits — every list before 1.9 and every new one); **protected** (with a password; the address views, ticks, polls and subscribes; structure, reset, delete, level and history need the password, 403 `checkoff_locked`); **private** (with a password; without the password the address gets nothing but the prompt, 403 `checkoff_private`). `set_level( $level, $password )` is the one writer: protecting an open list needs a password, afterwards `''` keeps the current one; open deletes password and listing; private deletes the listing. `Checkoff_Password::change( $checklist, $level, $password )` wraps it with the edit check and the cookie. The level was the user's decision after a review of the concept: the earlier two-ID model protected by the secrecy of the address only, so a list could be neither public nor really private.

Access as opened (`get_access()`): `edit`, `locked` (protected without password: ticks, but no structure) and `sealed` (private without password: `to_client()` returns `{id, access, level, protected, url}` and nothing of the list — no title; the page renders `renderSealed()`, a password form, and reloads after `cko_unlock`). `Checkoff_Shortcodes::lookup()` calls `Checkoff_Password::apply()` on every lookup (page, AJAX, REST alike), which calls `lock()` or `seal()`. **`request_checklist( $raw_id, $edit, $quota, $sealed_ok )` refuses a sealed list for everything** unless `$sealed_ok` — only unlock and lock pass it; `refuse_sealed()` is the same check for callers using `lookup()` directly (`Checkoff_Subscriptions::request()`: a private list's content is mailed only to whoever may see it).


**The public directory (`Checkoff_Directory`).** A protected list its owner marks (`set_listed()`, AJAX `cko_set_listed`, REST `PUT|DELETE …/listed`) appears in `[cko_lists]` and `GET /lists` — title, description, progress, link — most recently used first (`_cko_last_access`). Only protected: an open list there could be changed and deleted by anybody passing by, a private one may not be seen. **No approval, by the user's decision**; an administrator takes a list out in the IDs box (`cko_unlist`), the setting `checkoff_lists_enabled` (General, default on) empties the directory without touching the marks. `is_listed()` checks all three conditions, so a list made private or open leaves at once. The privacy text has a sentence while the directory is on.

**The password** (`Checkoff_Password`). WordPress's means, deliberately: **the hash** by `wp_hash_password()` / `wp_check_password()` in `_cko_password` — **not core's `post_password`, which is plain text** and visitors reuse passwords; **the unlock** like core's post-password cookie: one cookie per list (name from `wp_hash( post ID )`, so it names no list), 10 days, value `expires|wp_hash( post|expires|password hash, 'auth' )` — a new password ends every unlock — httponly, SameSite=Lax, secure on HTTPS; **API clients** send `X-CheckOff-Password` with each request instead (allowed in CORS). Wrong passwords: quota `unlock` per visitor plus `UNLOCK_PER_LIST` (50) per list from all visitors; once either is used up every unlock is refused for the hour, the right password included. Passwords are read unslashed and never sanitized (`from_request()`). There is no recovery without accounts: the access dialog says so, and an administrator can remove a forgotten password in the IDs box (the list becomes open); the list column shows a lock (protected) or a crossed eye (private) and a "Public" badge.

**One row per value, per round.** A tick writes exactly its row (`Checkoff_Values::set_value()`), so two people ticking at once never erase each other's ticks; a row holding neither value nor stage is deleted. `set_value()` stores the time (`set_at`, from `$at` for late ticks); `revalidate()` after a structure save keeps the times of re-checked values. The value is JSON in the table, so `true` stays `true`. The round is the index of the round in force (`Checkoff_Checklist::round_index()`, 0 without repetition) — a new round simply has no rows yet; see *Repetition and rounds*.

**Live update.** `sync_state()` is the one place computing what an open page shows besides the structure (values, stages, times, round, last round) plus an md5 fingerprint of it with the revision; `to_client()` and `ajax_poll()` both use it. The page polls `cko_poll` every `checkoff_sync_interval` seconds (default 20, 0 = off) while visible and not busy (unsaved edits, a save running, a note being typed, focus in a text field); an unchanged fingerprint is answered with the fingerprint alone, the structure is sent only for an older revision, and values of the page's own requests still in flight win over the answer. The answer also carries `upcoming` and, for the owner, the history index, so a page left open past midnight pages correctly. **Compare with `stableJSON()`, never `JSON.stringify()`**: the server lists values in another key order than the page's own ticks added them, and the plain comparison announced "Updated from another device" after every own tick (fixed in 3.3.1). A poll only reads: it closes no round and does not count as a visit.

**The board (2.5.0, a view, not a block — the user's design).** The container may carry `view: "board"` (absent = list) and `stages` (three own column names, absent = "Open · In progress · Done"); `sanitize_structure()` keeps both on the root only. While ticking (not editing) `renderBoard()` draws the sections as lanes (`.cko-board__lane`, sticky on phones, where the grid scrolls sideways) across three columns (`[data-board-cell][data-stage][data-lane]`); every entry is a card (`.cko-kcard`, through sub-lists). **Where a card stands follows from its values** — `Checkoff_Checklist::stage_of()` mirrored by `stageOf()`, both generic: an entry with a value is done when its block's `progress()` gives `total` 0 (a note, "not needed") or `done` reaching `total`, else in progress; without a value it is in progress when the entry's row carries the **stage** `doing` (`set_stage()`, AJAX `cko_set_value` with `stage`, REST `PUT …/values/{entry}` with `stage`; synced as `stages`, timed, queued offline, kept in the history, empty each round), else open. **Moving sets values, never the structure** (`moveCard()`): to open clears value and mark (undo toast), to in progress sets the stage (clearing a done value, undo toast), to done sets the block module's `doneValue()` where it has one (simple, due date, status, counter at its target, all weekdays) and otherwise opens the card for the value (`cardOpen`). **Adding on the board (3.8.0, the user's wish):** under every column of every lane `renderBoardAdd()` offers "+ Add item" — only while `canAddCards()` (may change the structure, round in force: not locked, not on a past or future round); its field (`boardAdding` = `<lane>|<stage>`) adds with Enter and stays open, Escape closes. `addCard()` appends the entry to the lane's section and saves the structure at once (`changed( true, 1 )`); the stage (`doing`) or the done value (`doneValue()`) is shown at once but sent from `afterSave` — callbacks `saveStructure()` runs after a successful save — because the server refuses values of an entry it does not know yet. Where done needs a value the card opens for it (as `moveCard()` does). Drag and drop is SortableJS per cell, grouped per lane (`initBoardSortable()`, touch delay so lists still scroll); the ⇄ button opens "Move to …" for touch and keyboard. **Switching is for everybody (2.5.1, the user's wish):** `renderViewSwitch()` sits beside the title in tick mode (`.cko-head__row`, `.cko-viewswitch`, list / kanban icons); the choice holds on this device (`localStorage` `cko_view_<id>`, `viewOf()`), and choosing the list's own view again forgets it. `view` in the structure is only the default everybody sees first, set while editing in the panel "View" (`renderViewPanel()`) together with the column names; editing always shows the list. Open entries in progress say so in mails (`open_items_of()` prefixes the note with the column's name).

**Ticking without a connection (2.4.0).** `setValue()` / `setStage()` → `sendChange()`; a request failing with status 0 (no network) puts the change into `localStorage` `cko_queue_<id>` (key = entry, or entry + `|stage`, → `{item, kind, value, at}`; a newer change replaces a waiting one) and the save state turns `offline` (`wifi-off`). `flushQueue()` sends them one by one with `at` — on the `online` event, instead of a poll, and on opening the page (`startQueue()` first shows the waiting values); a refusal drops the tick with a toast, a missing connection stops the flush. While anything waits, `isBusy()` holds the poll back. The server (`set_value( $id, $raw, $at )`, AJAX/REST `at`) stores that time — clamped to now and to `LATE_TICK_MAX` (a week) back — and refuses a tick made before the current round began with 409 `checkoff_round_over`, so a late tick never lands in the next day. Only values queue; a structure save without a connection fails as before.

**Structure and values are separate on purpose.** A tick sends one entry (`cko_set_value`); an edit sends the whole tree (`cko_save_structure`) with the revision it was based on. **The primary key of `checkoff_versions` is the lock:** saving inserts revision + 1, and of two saves based on the same revision only one can — the other gets 409, so two tabs cannot overwrite each other, also across processes. An object memoises its version, so a long-lived `Checkoff_Checklist` stays at its revision (tests re-instantiate). On every structure save the values of the round in force are re-validated: values of removed entries go, the rest are checked against the (possibly changed) block settings via `revalidate_value()`; without a history, older versions are pruned at once.

**Tree format.** A checklist has **no type**: the top level is a container `{id, kind:"checklist", title, description, items[], recurrence, view?, stages?}` whose items are blocks only — the stacked building blocks, drawn as sections (heading, no frame). Block: `{id, kind:"block", type, title, description, settings, items[]}`; leaf: `{id, kind:"item", label}`. A block's items are leaves and — where `supports_children()` says so, which every built-in block does since 1.3.0 — nested blocks, drawn framed. Depth counts blocks from the top level (the container is level 0).

`Checkoff_Checklist::sanitize_structure()` validates on write **and on read**: unknown types become `simple`, unsupported children are dropped, duplicate/invalid IDs are replaced, depth (`checkoff_max_depth`) and size (`checkoff_max_nodes`) are enforced by dropping the excess rather than refusing the save. A raw tree that is not a container is read as one (its items must be blocks).

### Building blocks

`includes/lib/blocks/`: abstract `Checkoff_Block_Type` plus one class per block (`simple`, `status`, `deadline`, `weekdays`, `color_scale`, `number_scale`, `measurement`, `choice`, `counter`, `note`). A block class is the only place that knows its settings and allowed values (`default_settings`, `settings_schema`, `sanitize_settings`, `sanitize_value`, `revalidate_value`, `value_for_display`). `Checkoff_Block_Types` is the registry (filter `checkoff_block_types`), knows which blocks are switched on (`checkoff_block_<key>_enabled`, default on; `simple` always) and hands the definitions to the frontend, so the builder never offers what the server would refuse.

**Never rename a block key** — stored checklists refer to it.

**An entry may carry data of its own** in the structure, beside its label: `{id, kind:"item", label, data}`. Only the block type knows it (`sanitize_item_data()`, empty by default, so the key is absent for every other block and for unchanged old trees); it is set while editing, so ticking cannot change it, and it is dropped when the block changes type (server and `changeType()` alike). So far only the due date: `deadline` stores `data.due` (Y-m-d). `describe_item( $item, $value, $settings, $now )` is the one wording of an entry's state with that data ("overdue since …", "due today", "due on …"); `open_items_of()` carries it as `note`, the mails print it, and `$now` is threaded through from `checklist_data()` like everything else in a mail.

The colour scale (1.11.0) has per-block `labels` (own names left to right, missing ones fall back to the site's) and `reverse` (green first); `Checkoff_Block_Color_Scale::steps_for( $settings )` is the one place that combines them with the site's scale, mirrored by `scaleFor()` beside the colour scale's module in the browser. The value stays the position from the left.

The 1.5.0 blocks in short: `status` stores `'done'` or `'skip'` — a skipped entry returns `{done:0,total:0}` and so leaves the progress (the mail marks it ⊘); `deadline` extends `simple` (value `true`) with the due date and the setting `soon` (days before the date marked as due soon); `measurement` stores a number rounded to `decimals`, `min`/`max` are numbers or `''`, done = inside the range or, without one, entered (`in_range()`, mirrored by `inRange()` beside the measurement module in the browser); `choice` stores the **index** of an answer in `settings.options` (1–12 answers, renaming one keeps the choices, removing one drops the choices beyond the end). Settings field types for the builder: `number`, `select`, `checkbox`, `days`, and since 1.5.0 `text`, `decimal` (accepts a decimal comma) and `options` (one answer per line).

**There is no switch (removed in 3.2.0, by the user's decision: every block works the same way).** A block never holds a value of its own and never chooses among its children: values belong to entries only, every sub-list counts. `leaf_map( $structure )` maps entries, nothing else. A stored `switch` type is unknown and read as `simple`, so its variants are ordinary sub-lists. Don't add block types that hold a value or pick children — that was the special case the rule exists against.

Weekdays with the weekly reset store `{days, week:"2026-W45"}`; the week is always set by the server, `value_for_display()` hides last week's ticks without deleting them, and `revalidate_value()` keeps the stored week so re-saving the structure cannot move old ticks into the current week.

### Frontend

`renderBlock( block, depth )` draws the container (depth 0: `header.cko-head` — while ticking title (+ view switch), description (`.cko-head__desc`), progress, then the round line (chip with ‹ ›, then dates and rule as one quiet `.cko-round__when`); while editing only the title field, then description field and the repetition panel (3.7.0: no progress and no round while editing); then `.cko-sections` and the dashed "Add building block" button that opens the picker), a section (depth 1: no frame in tick mode, framed while editing; an untitled section shows no heading outside edit mode) or a nested sub-list (framed). In `locate()` the container is depth 0. A section's heading row carries, in edit mode, the drag handle, the type icon, the title field, the settings toggle (`settingsOpen[id]`, panel with type, settings and description) and the ⋯ menu (`openBlockMenu()`: add sub-list, duplicate, up, down, delete); in tick mode a collapse chevron. While ticking the type icon is quiet (`.cko-block__type--quiet`: no tile, muted), and a section's progress bar shows only when it has more than one step — a bar for one entry repeats that entry.

**Two modes, never mixed.** "Tick off" shows the value controls only, "Edit" the structure only (label fields, handles, delete ×, a `.cko-newentry` field at the end of every block: Enter adds and stays there, Backspace on an empty field goes to the last entry). The switch is the segmented `.cko-mode` in `.cko-bar`; a locked (protected) view shows "Unlock to edit" instead, a list locked by a conflict neither. A list created empty opens in edit mode (`#edit`) with focus in its first entry field.

**No block-specific code outside the blocks (3.1.0, the user's rule: every block works the same way).** Everything that differs between building blocks lives in the block's PHP class and, in the browser, in its module in `BLOCK_TYPES` (section *BLOCK TYPES* of `frontend.js`), with the defaults in `BASE_TYPE`: `progress( value, settings )` (twin of the PHP method), `control( view, c )`, `summary()` (closed card), `doneValue()` (board), `itemEditor()` / `itemMeta()` (entry data such as the due date), `notes()` and `icon` — the same set for every block, none used by one block only. The rest of the file — list, board, editor, progress, history — only calls `typeOf( key )`, never compares a block's type; the CSS styles states (`.cko-item.is-done`, `.is-settled` for a value outside the count), not types. What a module needs from the server beyond settings comes from `Checkoff_Block_Type::client_data()` (`data` in the definitions: the colour scale, the current week), not from the global config. A new block is a PHP class plus a module, nothing else. **Add-ons** register the class through `checkoff_block_types` and the module through `window.checkoffBlockTypes.push( factory | module )` — a factory gets the kit (`el`, `icon`, `iconButton`, `button`, `format`, `toast`, `i18n`, `blockDef`, `hasValue`); before or after `frontend.js` has run, merged over the built-in's methods for a built-in key (`registerBlockType()`); they enqueue it on the action `checkoff_enqueue_frontend_assets` (argument: the frontend's handle, to depend on). `tools/smoke-test.js` checks both ways of registering.

**The UI kit lives at the top of `frontend.js`**: `icon()` / `typeIcon()` (the block module's `icon`, else the PHP class's symbol), `iconButton()`, `button()`, `toast()` (body-level `.cko-toasts`, optional action), `openMenu( anchor, items, content )` (body-level `.cko-menu`, below the anchor, else above it, else — a long picker on a phone — as high as the viewport and scrolling inside; always kept inside the viewport; closes on outside click, Escape and resize, arrow keys move) and `confirmDialog()` (a `<dialog>`, returns a Promise). Menus and toasts sit outside `.cko-app`, so they carry the tokens themselves. `enhanceForms()` puts the icons into the server-rendered create, open and template forms.

**Deleting is undone, not confirmed.** `remove()` deletes at once and offers "Undo" in a toast for 6 s, and the structure save waits that long (`changed( true, 6000 )`) so an undone delete never reaches the server. Only resetting all ticks and deleting the whole checklist ask first (`confirmDialog()`).

**Sorting is drag and drop** (SortableJS on every `[data-sortable]`, handle `.cko-handle`, `touch-action: none` so it works by touch); `onEnd` calls `moveTo( parent, from, to )`, which changes the model and redraws — Sortable's own DOM move is overwritten by that render. Sections and sub-lists can also be moved with the ⋯ menu, entries with Alt+↑/↓ in their field.

**Third-party code is bundled, never loaded from a CDN** (a CDN request would hand every visitor's IP to a third party and need a line in the privacy text): `assets/vendor/sortablejs/` (SortableJS 1.15.6, MIT) and `assets/vendor/lucide/icons.js` (53 Lucide 0.460.0 icons, ISC, as `window.checkoffIcons` — add an icon by copying its SVG body from lucide-static of that version). Both are registered as dependencies of the frontend script. Licences in their folders and in `readme.txt`.

**No CSS framework, on purpose.** A global one (Bootstrap, Tailwind's preflight) restyles the theme's own buttons and headings. `frontend.css` is a small design system of its own: tokens as custom properties on the container classes (`--cko-accent`, `--cko-done`, `--cko-danger`, `--cko-radius`, `--cko-control`, …), surfaces mixed from `currentColor` so light and dark themes both work, `Canvas` / `CanvasText` for popovers. **Every component rule is scoped `:is(<containers>) .cko-…`**: themes style `button:hover`, `[type=button]:focus` and `input[type=text]` at (0,1,1)–(0,2,1), and single-class rules lost to them — under Hello Elementor a hovered button turned pink and every field got a dark border. A new rule gets the same prefix.

**Design settings (`Checkoff_Design`, 3.5.0).** Tab Design (`checkoff_design_accent`, `_accent_contrast`, `_done`, `_danger` — hex or `''` for CheckOff's own; `_radius` px or `''`; `_size` compact|normal|large → `--cko-control`; `_font` theme|system). `css()` writes only what differs from the defaults, as CheckOff's own custom properties on the container list (`CONTAINERS`), added with `wp_add_inline_style()` after `frontend.css` in `enqueue_frontend_assets()` — one class, so a theme's stronger selector still wins. **With Elementor active** (`elementor()`: `ELEMENTOR_VERSION` / `elementor/loaded`, filter `checkoff_design_use_elementor`) colours and fonts come from the kit: `--cko-accent: var(--e-global-color-primary, <own or default>)`, `--cko-done: var(--e-global-color-accent, …)`, text font `--e-global-typography-text-font-family`, headings (`HEADINGS`) the primary font; the own values are the fallback, radius, size and warning colour stay the plugin's. The tab then shows `notice()` above its fields (tab key `notice`, rendered by `settings_section()`). Field type `color` (admin API) is WordPress's colour picker (`wp-color-picker`, admin.js), empty allowed. **The child theme sets no `--cko-*` design variable any more** (1.1.0): its `body.cko-theme` selector would override these settings. Assertions in `tools/checklist-test.php` (*design settings*).

**Theming variables, and what they must keep.** Tokens are set on the container classes (first rule of `frontend.css`); a theme overrides them with a stronger selector. `--cko-accent` is the accent as a surface, `--cko-accent-contrast` text on it, **`--cko-accent-text` (1.11.0, default the accent) the accent as text or icon colour** — every `color:` that used the accent uses it now, so a light brand colour can be made readable without touching the surfaces. The surface variables `--cko-card-bg/-border/-padding` (`.cko-card`, `.cko-history`, `.cko-subscribe`) and `--cko-panel-bg/-border` (`.cko-panel`, blocks while editing) are **deliberately not defined**: each rule reads `var(--cko-card-padding, <its own old value>)`, so nothing changes until a theme sets one. Keep that pattern for new variables — the readme promises existing names and defaults never change. Field-width safety rules use `:where()` so they weigh nothing against a field's own width (`.cko-input--short`); a first version without it widened the unit field. Contrast and overflow were checked with a Playwright audit at 390/820/1280 px with a light (`#E8C547`) and a dark (`#30323D`) accent, and tick/edit mode were compared pixel by pixel with the 1.10 styles.

**The checklist page** (`Checkoff_Checklist_Page`, 1.11.0): the chosen page (`checkoff_checklist_page`), else the first published page with `[cko_app]`, a page template that adds it (filter `checkoff_checklist_page_templates`, the child theme's by default), or `[cko_checklist]` without a fixed `id` — in `post_content` or `_elementor_data`, by menu order then age. Cached in the transient `checkoff_detected_page` for a day, forgotten whenever a page is saved, trashed or deleted. `Checkoff_Checklist::page_url()` delegates to it, so the REST API, mails, the share menu and forms all follow. While nothing is chosen an admin notice (dashboard, plugins, CheckOff screens) says where links lead.

**Wording (2.0.0):** visitors see "link to the checklist" and "ID of the checklist", with a hint per level (`link_hint_<level>`); the levels are "Open / Protected / Private" ("Offen / Geschützt / Privat"; `level_open` is `_x( 'Open', 'access level' )` because "Open" the button is "Öffnen"), chosen in `accessDialog()`. **There is no "More actions" section any more (2.1.0):** whoever may edit gets icon buttons in `.cko-bar__end` beside the bell and the share button, in both modes — the lock (`.cko-lockdevice`, only with a password: lock on this device, a button of its own by the user's wish), the shield (`.cko-access`, label names the level; `openAccessMenu()` opens the access dialog directly, or — while `canList()`, i.e. protected with the directory on — a menu with it and show publicly / do not any more, showing asks first with `confirmDialog()`) and ⋯ (`openMoreMenu()`: clear all ticks, delete the checklist). The `.cko-more*` classes are gone. "Private" means the level, never an ID any more. Code and docs say "public ID". Icons per level in `LEVEL_ICONS` (`lock-open`, `lock`, `eye-off`).

`[cko_checklist]` embeds the checklist as JSON in `script.cko-data` (encoded with `JSON_HEX_*`, so a title cannot close the script element) and `assets/js/frontend.js` draws it. Text inputs update the model without redrawing (focus and caret stay); clicks redraw with focus restored by `data-focus` keys. The progress bar is computed in the browser (see *Repetition and rounds* for its server twin). The recently opened list is localStorage only (`cko_recent`); a private list is remembered without its title (`{id, private: true}`, shown as "Private checklist"), and `.cko-recent__clear` empties it after asking. Below 480 px the mode switch hides its labels (`aria-label`/`title` keep the names) so the bar stays one row. Assets are registered on `wp_enqueue_scripts` but enqueued only by the shortcodes (`Checkoff::enqueue_frontend_assets()`).

Pages carrying `?cko=` get `noindex, nofollow` (`Checkoff_Post_Types::noindex_checklist_views()`), because the address contains the secret.

### Security: quotas, visitors, headers, wp-admin

**Every hourly quota lives in `Checkoff_Quota`** and is taken in the one lookup both channels share (`request_checklist( $raw_id, $edit, $quota )`), or in the shared methods for creating (`create_checklist()`) and subscribing (`Checkoff_Subscriptions::request()`) — a quota checked in only one channel would be bypassed through the other. `take()` refuses with 429 `checkoff_quota_<action>` and `retry_after`, else counts; `refusal()` checks without counting.

| Action | Counts | Option (default, 0 = unlimited) |
|---|---|---|
| `create` | new checklists per visitor / **all visitors together** | `checkoff_create_per_hour` (10) / `checkoff_create_total_per_hour` (100) |
| `tick` | values written (set, clear, notes typed) | `checkoff_ticks_per_hour` (1200) |
| `edit` | structure saves, PATCH, reset, delete, history delete | `checkoff_edits_per_hour` (600) |
| `subscribe` | subscription requests | `checkoff_subscribe_per_hour` (5) |
| — | unknown IDs (then every lookup refused) | `checkoff_failed_lookups_per_hour` (20), in `lookup()` |
| `unlock` | wrong passwords (then every unlock refused); plus 50 per list from all visitors | `checkoff_unlock_per_hour` (10), in `Checkoff_Password::verify()` |

Reads (open, poll, history) take no quota. The page saves after a pause in typing (700 ms), which is why tick and edit quotas are generous: they stop scripts, not people. The AJAX handlers send `Retry-After` too (`send_retry_after()`).

**`Checkoff_Rate_Limit` only counts**, per visitor or for all visitors (`$all_visitors`), as a salted hash in a transient. The visitor (`visitor()`) is an IPv4 address or an **IPv6 /64** (one connection gets a whole /64; per address it would be no limit), from `checkoff_ip_source` — the connection by default, or X-Forwarded-For (first entry), X-Real-IP, CF-Connecting-IP for sites behind a proxy. A header is only trustworthy behind a proxy that sets it, which the setting's description says; an invalid value counts as `''` (all such requests share one count, erring towards limiting). Tests give every run its own IPv6 /64.

**Pages with `?cko=`** get `no-store` cache headers, `DONOTCACHEPAGE`/`DONOTCACHEOBJECT`/`DONOTCDN`, `Referrer-Policy: no-referrer` and `X-Robots-Tag` (`Checkoff_Post_Types::protect_checklist_views()`), besides the `noindex` robots meta: the address carries the secret.

**wp-admin is for administrators.** Both post types map every primitive capability to `Checkoff_Post_Types::admin_capability()` (`manage_options`, filter `checkoff_admin_capability`) and creating to `do_not_allow` (`admin_capabilities()`): with the post defaults every editor could read every visitor's IDs. Settings, the test mail and the log stay `manage_options`.

### REST API (`Checkoff_Rest_Api`)

Namespace `checkoff/v1`. Access by `checkoff_rest_access`: `public` (everybody, by the ID — the default), `users` (logged-in users only, 401 otherwise, via the routes' `permission()`) or `off` (no routes); a site from 1.6/1.7 still has `checkoff_rest_enabled`, which `access()` reads until the new setting is saved. Every answer of the namespace gets `Cache-Control: no-store`, `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer` and, on 429, `Retry-After` (`secure_response()` on `rest_post_dispatch`). **Everything the website does, by the same code — never a second implementation of a rule:**

| Route | Website twin |
|---|---|
| `GET /blocks`, `GET /templates` | the builder's block definitions, the template gallery |
| `POST /checklists` `{title, template \| structure}` | `cko_create`, through `Checkoff_Shortcodes::create_checklist()` (login setting, hourly limit) |
| `GET /checklists/{id}` | opening the page: `lookup()`, `touch()`, `to_client()` (+ `progress`) |
| `GET /checklists/{id}/state` | `cko_poll` — reads only, no visit |
| `PUT …/structure`, `PATCH /checklists/{id}` | `cko_save_structure`, revision check → 409 |
| `PUT\|DELETE …/values/{entry}` `{value?, stage?, at?, round?}`, `DELETE …/values` | `cko_set_value` (with `stage`), `cko_reset_values` |
| `DELETE /checklists/{id}` | `cko_delete` |
| `POST\|DELETE …/unlock`, `PUT\|DELETE …/password`, `PUT …/access` | `cko_unlock`, `cko_lock`, `cko_set_password`, `cko_remove_password`, `cko_set_access` — through `Checkoff_Password::change()` |
| `PUT\|DELETE …/listed`, `GET /lists` | `cko_set_listed`, `[cko_lists]` — through `Checkoff_Directory` |
| `GET\|DELETE …/rounds` | `cko_history`, `cko_history_delete` — edit ID only, through `Checkoff_Shortcodes::history_data()` |
| `GET …/upcoming/{number}` | `cko_upcoming_round` — whoever may tick, through `Checkoff_Shortcodes::upcoming_round()` |
| `POST …/subscriptions` `{email, consent}` | `cko_subscribe`, through `Checkoff_Subscriptions::request()` |

No route checks a capability **on purpose**: the ID in the path is the authorisation, as `?cko=` is on the page (`permission()` only adds the site's choice of logged-in users only). The REST `checklist( $request, $edit, $quota )` and the page's `ajax_checklist()` both call **`Checkoff_Shortcodes::request_checklist()`** — the rate-limited `lookup()`, 403 `checkoff_locked` / `checkoff_private` where the level needs the password, and the request's quota. Errors are `WP_Error`s with `status` — `lookup()`, `create_checklist()` and `request()` carry it themselves (`Checkoff_Shortcodes::error_status()` reads it for the AJAX answers), model errors get it in `model_error()` (409 conflict, 404 unknown entry). A structure is size-checked against `Checkoff_Shortcodes::MAX_PAYLOAD` like the page's (413). A rule added to an AJAX handler belongs in the shared method, or REST silently lacks it. Assertions in `tools/rest-test.php` (dispatched through `rest_do_request()`, a fresh fake IP per run so limits do not carry over).

### Templates (`Checkoff_Templates`)

A template is an ordinary checklist an administrator built on the website and marked in wp-admin (box "Template": `_cko_template` = '1', `_cko_template_desc`, `_cko_template_key`; for several at once the list's bulk edit offers "Template: no change / offer / do not offer" — `Checkoff_Post_Meta::render_bulk_edit()` in the ID column's slot, applied per post on `save_post` by `save_bulk_edit()` with its own nonce, keeping each description; quick edit stays removed). Visitors refer to it only by the key — never by post ID or one of its IDs, which would let them edit or tick the template itself. `create_from( $key, $title, $start )` makes a new checklist with a copy of the structure (title of the copy or of the template, repetition restarting today — or on `$start`, checked by `start_date()`: a date from today to a year ahead, else today; the create form shows `[data-cko-start]` while a template with `data-repeats` is chosen, `syncStartField()`; AJAX/REST `start`, 3.6.0) and nothing else: no values, no subscriptions; later changes to the template do not reach copies. Offered in the create form (`type` value `tpl:<key>`, beside "Empty checklist" — the form asks for no block type, since a checklist has none: an empty one starts as one untitled simple block and gets its building blocks while editing; without templates the form is name and button only; **per shortcode since 1.12.0** — `[cko_create templates="no"]` (and `[cko_app templates="no"]`, passed on) hides them, `template="…"` preselects, both together give a form without choice that always starts from that template; the former setting `checkoff_templates_in_form` has no field any more, but a stored `''` stays the default (`Checkoff_Templates::shown_by_default()`) so such sites do not change; yes/no attributes go through `Checkoff_Shortcodes::attribute_flag()`) and by `[cko_templates]`. A copy opens ready to use (`edit: false` in the create answer), an empty list in edit mode. The cleanup never deletes a template.

### Repetition and rounds

`Checkoff_Recurrence` holds the rule — `freq` (none|daily|weekly|monthly), `interval`, `start`, `end` (never|count|until), `count`, `until` — stored as `recurrence` on the **top-level block** of the structure, so it travels with structure saves and their revision; `sanitize_structure()` adds it to the root only. Invalid rules turn repetition off rather than guessing.

**Rounds are computed, never counted.** `current( $now )` derives the round in force from the rule and the clock (site time zone; a round runs from 00:00 of its first day to 00:00 of the next round's). Before the start the first round is in force; after the last it stays in force, `finished`. Monthly rounds keep the start's day of the month or take the month's last day (31 Jan → 28 Feb → 31 Mar).

**A new round starts empty, without a write.** Values are read from and written to the round in force (`round_index( $now )`); when the clock passes into the next round, its rows do not exist yet. Nothing is closed, copied or summarised — "last time" (`get_last_round( $now )`: number, done, total, open entries, closed) is computed from the rows of the round before and the structure version in force when it ended, for mails and the page. A late tick (`$at` before the round in force began) is refused with 409 `checkoff_round_over`. **Changing the rule** moves the rows of the round in force into the round in force under the new rule and deletes the rest (their numbers belong to the old rule).

**The history of rounds (`Checkoff_History`) is virtual and off by default** (`checkoff_history_enabled`; `checkoff_history_days`, default 90). A past round is the rows of an earlier round number, drawn with `Checkoff_Versions::at( round end )` — the structure saved last before it ended (else the newest), so a later rename, reordered choice or changed unit cannot falsify the past; number and dates come from the rule, progress from rows + structure. Off: only the round in force and the one before stay — `keep_to_retention()` deletes older rows after every write, the daily cron (`checkoff_history_prune`, always scheduled) for lists nobody opens. On: past rounds stay for the configured days after they ended; the cron (`prune_all()` → `prune()`) deletes older rows and the versions no kept round needs. Switching it off deletes everything before the last round (`delete_all()`); the owner can delete a list's history (`clear()`, ⋯ menu); deleting a checklist deletes its rows in both tables (`Checkoff_Schema::delete_for_checklist()` on `before_delete_post`). Rounds without rows are no history. The privacy text has a sentence for each state. wp-admin shows a list's kept rounds in a side box on its screen.

**Paging, not summaries (2.2.0, the user's wish).** The page shows no summary box any more: `to_client()` gives an edit view (`shows_times()`: may edit, history on) `times` (entry → unix time, also in the poll) and `history {rounds, index, days}` — `index()` is the kept rounds (number, dates in the site's format), oldest first. Beside the round chip ‹ (and, on a past round, ›) page through them; `showRound()` loads one with `cko_history_round` / REST `GET …/rounds/{number}` (`round_view( $checklist, $number )`: structure then, values, stages, times, progress; 404 `checkoff_round_not_kept`) and swaps it into `structure`/`values`/`times`, keeping the live state in `this.live`; the round is drawn by the ordinary renderer in tick mode, `.cko-card--past` with every control in `.cko-sections` disabled, under `.cko-pastbar` with "Back to the current round" (`showLive()`), the mode switch hidden and polling paused (`isBusy()`). Entries show their time (`renderTime()`, `time.cko-item__time`: the time today, else date and time, in the browser's zone). `rounds()` (the worded summaries) still answers `GET …/rounds` for API clients. While paging is possible, the "last time" line of the round chip is left out. Assertions in `tools/checklist-test.php` (*history*, *times*) and `tools/rest-test.php`.

**Ticking ahead (3.3.0, the user's wish).** `Checkoff_Checklist::upcoming( $now )` gives the rounds after the one in force that may be ticked — `checkoff_upcoming_rounds` (General, "Tick ahead", default `UPCOMING_DEFAULT` 8, max 52, 0 = off), never beyond the end of the series, none for a finished one. `set_value()` / `set_stage()` take the round's **number** as last argument (`target_round()`: null or the round in force → as before with `moment()`; a round ahead → its index, `at` = now; anything else 409 `checkoff_round_not_open`). Values that depend on the date are sanitized and shown for that round: `Checkoff_Block_Type::at_time( $start, $callback )` sets the clock `now()` reads (weekdays' `current_week()`), so a weekday tick ahead carries the week of its round. `upcoming_view( $number )` is the round as the page shows it (current structure, values revalidated and displayable at the round's clock, stages, times, progress); `to_client()` carries `upcoming` (number and dates) for every view that may tick. A structure save revalidates the rounds ahead too; deleting the history (`Checkoff_History::clear()`, now `clear_before()`) keeps them, `kept()` never counts them; a rule change still deletes them with the rest — the repetition panel warns while any round ahead has ticks (`ticked` in `upcoming`). Switching rounds first sends notes still waiting for a pause in typing (`flushNotes()`), or they would land in the round paged to. AJAX `cko_set_value` with `round`, `cko_upcoming_round`; REST `round` on `PUT|DELETE …/values/{entry}`, `GET …/upcoming/{number}` (both through `Checkoff_Shortcodes::upcoming_round()`). In the browser `roundNeighbours()` pages through past, live and ahead alike; `showRound()` loads a round ahead into `this.future` (live state in `this.live`), drawn as the ordinary list under `.cko-pastbar--future` (`renderFutureBar()`), controls active, mode switch hidden, polling paused; `sendChange()` adds `round`, and the offline queue keys such changes `<round>:<entry>` and sends them without `at`. Assertions in `tools/checklist-test.php` (*ticking ahead*) and `tools/rest-test.php`.

**Progress has two implementations, on purpose.** The server's is `Checkoff_Block_Type::progress()` per block (`Checkoff_Checklist::progress_of()` / `open_items_of()`), used for mails and summaries; the browser draws its bar with the same rule — `Checklist.prototype.progress` sums the block modules' `progress()` over every entry. Change both together. `describe_value()` on the block types is the one wording of a value (admin outline, mails).

### E-mail subscriptions (`Checkoff_Subscriptions`, `Checkoff_Mailer`, `Checkoff_Mail_Log`)

Built like the subscriptions of MixMyMeals, with one rule above everything: **store as little personal data as possible.**

- A subscription (`cko_subscription`, shown under the CheckOff menu, no edit screen) stores `_cko_sub_email`, `_cko_sub_checklist`, `_cko_sub_status` (pending|active), `_cko_sub_confirmed` (time of consent — the proof double opt-in needs) and `_cko_sub_sent` (send key → time). **No name, no IP, no user agent.** The post title is the masked address, so wp-admin never shows the full one. `tools/subscriptions-test.php` asserts the exact set of meta keys of a pending subscription — adding a field means changing that assertion knowingly, and the privacy text.
- **No token is stored.** Links carry `hash_hmac( sub ID | post_date_gmt | action, wp_salt )`; a deleted subscription's links stop working by themselves.
- **Unsubscribing deletes the post**, as do deleting the checklist, trashing the subscription, the privacy eraser and uninstalling the plugin. Unconfirmed subscriptions are deleted after `checkoff_subscription_pending_hours`. There is deliberately **no suppression list** — it would be a list of addresses kept after their owners left; double opt-in already stops third parties signing somebody up.
- **A GET never confirms or unsubscribes.** Mail scanners open links; the GET page shows a button whose POST acts. Mail clients' one-click unsubscribe (`List-Unsubscribe-Post`, RFC 8058) is a POST and works directly.
- The subscribe answer never tells whether an address was subscribed already. Limits: the `subscribe` quota per visitor (`Checkoff_Quota`), `checkoff_subscriptions_per_checklist`, and `Checkoff_Mailer::RATE_LIMIT_PER_HOUR` per address (filter `checkoff_mail_rate_limit_per_hour`).

**Sending rules** (`checkoff_mail_rules`, defaults in `default_rules()` until the option is saved): trigger + time + subject + template + `only_open`. Triggers: `on_confirm` (sent by `confirm()`), `each_day`, `round_start`, `round_last_day`, `round_end`, `series_end`. `occurrences()` gives the latest occurrence per rule; the 15-minute cron (`checkoff_mail_dispatch`) sends it once it is past, after the confirmation, and not more than `GRACE` (a day) late — a site that was down for a week sends no backlog. Sent occurrences are remembered under `trigger|time|template|occurrence`, so editing a subject does not resend. `only_open` settles a reminder without mailing when everything is done. `dispatch( $now )` takes the time as a parameter and threads it through rollover, progress and the mail contents — tests depend on that.

**Mails are templates**, as in MixMyMeals: `templates/emails/*.html` with `{{ placeholders }}` (escaped by suffix: `_html` → `wp_kses_post`, `_url` → `esc_url`, else `esc_html`), wrapped in `layout.html`; `confirm.html` is the double opt-in mail (subject setting `checkoff_confirm_subject`). Lookup: child theme → parent theme → plugin, each asking `<dir>/<locale>/` first — that is how the mails are translated (`templates/emails/de_DE/`). Template comments are stripped before sending. `mail_vars()` builds every placeholder for every mail (since 3.6.0 `ahead_html` / `ahead_items_html` / `ahead_count`: what is ticked in advance for the round after the one in force, from `checklist_data()`'s `ahead` — `upcoming_view()` of the next round; the reminder template shows it); the test button fills them from `demo_data()`, a made-up checklist, so no visitor's list lands in an admin inbox.

**Send log** (`checkoff_mail_log`, opt-in): time, masked address, subject, status; dropped after `checkoff_mail_log_days`, emptied when switched off.

### Settings

Tabs General (incl. live update interval and public checklists), Building blocks, Design, Limits, E-mail, Maintenance under CheckOff → Settings (`edit.php?post_type=cko_checklist&page=checkoff_settings`). Fields are declared in `Checkoff_Settings::settings_fields()` (filter `checkoff_settings_fields`) and rendered by type in `Checkoff_Admin_API::display_field()` (filter `checkoff_render_settings_field`). Every reader passes its default to `get_option()`, since `register_setting()` defaults only exist during admin requests.

### Cleanup and uninstall

`Checkoff_Cleanup` deletes checklists unused for `checkoff_cleanup_inactive_days` (off by default) via daily cron. `uninstall.php` always removes options (send log included), transients, cron events and **every subscription** (without the plugin nobody could unsubscribe), and deletes checklists — and drops both tables (`Checkoff_Schema::drop()`) — only with `checkoff_delete_data_on_uninstall`; otherwise it keeps only the round in force and the newest version of each list.

The privacy text (`Checkoff_Privacy::policy_text()`) follows the settings: the subscription paragraphs appear only while subscriptions are on, the log sentence only while the log is on. Anything that changes what is stored about a person changes that text.
